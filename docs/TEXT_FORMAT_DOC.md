# 《Crisis Beat》（PS1 日版）文本压缩与存储位置技术文档

> 依据 SLPS_014.exe 逆向与多轮实测确认，配套代码见 `.temp/cb/codecs.py`、`disc_lzss.py`、`engine137.py`、`engine137b.py`。

## 一、结论速览

1. **对话/字幕文本本身不压缩**：在场景包解压后，文本以明文 token 流形式存放，用 0x00 字节流终止，块间以零填充。
2. **文本所在文件是 `DATA.0`**：光盘数据轨起始（LBA 1184，逻辑地址 0x250000 起），内含场景包条目表（实测 513 条，旧文档称 2037 条）与全部场景包。
3. **文本所在的场景包/条目是压缩的**：采用游戏自研的 pak 块流压缩格式，解压器由 `codecs.py` 完整复刻（顶层 0x8001E0F0，块分发 0x8001DC8C）。
4. **文本编码是双字节扩展表**：码 0x01-0xEF 单字节；0xF0-0x1AF 用 `FF xx`；0x1E0-0x2DF 用 `FE xx`；控制字节 F0/F1/F2/F3/F4/F5/F6。

## 二、两层结构：先解包，后读文本

### 2.1 顶层：DATA.0 的条目表

- 光盘镜像 `Crisis Beat (Japan).bin`，数据轨起始 LBA 1184（逻辑 0x250000 起；早期文档 "0x290000" 为同一位置的旧表述，见 `tools/README.md` 偏移基准）。
- 条目表位于 DATA.0 开头（LBA 1184 起 4 个扇区），每项 4 字节小端 LE32，实测 513 条（旧文档称 2037，以解析器结果为准）。
- 每条目描述一个场景包的起始逻辑偏移；条目 `[i]` 到 `[i+1]` 之间即该场景包的数据区。
- `disc_lzss.py` 实现条目表解析与按条目取数。

### 2.2 场景包（entry）压缩格式

场景包整体是自研 pak 格式的压缩流，格式如下：

```
连续块流：
  while (src[p] != 0x00):
    块 = decode_block(src, p, out, out_start)
    p += consumed
    out 写入 dst + 8192*块号     # 引擎延迟槽 addiu s1, s1, 8192
  （0x00 结束）
```

每个块由 1 字节 tag 开头，按 tag 分发到不同解码器：

| tag | 解码器 | 说明 |
|----|--------|------|
| 0x14 | 字典 nibble | `[14][n16][16字节字典][n控制字节]`，每字节拆高低 nibble 索引字典 |
| 0x20 | LZSS 变体 | c<0x80 字面量；0x80<=c<0xC0 长匹配(off16 绝对)；>=0xC0 短匹配(off8 相对) |
| 0x30 | RLE8 | `[count][ch]` 序列，count=0 结束 |
| 0x31 | RLE16 | `[count16][ch]` 序列 |
| 0x40 | RLE 单次 | `[40][ch][count16]` |
| 0x70 | 位选择 RLE | n 组 `[fill][4B LE32 标志]`，标志位 1=fill、0=字面量，MSB 先 |
| 0x71 | 经典 RLE | 控制字节 c：0=结束；c&0x80 → `[ch]x(c&0x7F)`；否则 c 个字面量 |
| 0x72 | 平面拆分 | `[72][len16][内嵌 0x73/0x74 流]` → 解压后前半→偶数位、后半→奇数位 |
| 0x73 | LZSS | 直接字节；控制 0 结束、127 长重复、126 短重复、c&0x80 匹配、else 字面量 |
| 0x74 | LZSS + 映射表 | `[74][n][n字节字典][n个LE16][LZSS流]`，建表+读半字映射 |
| 0xFF | 原样拷贝 | `[FF][len_lo][len_hi][data...]` |

- 注意 0x72 内嵌的 0x73/0x74 流：引擎内嵌流解码为**临时缓冲**，再把临时缓冲的前半写偶数位、后半写奇数位（plane split），用于几何/字形数据的奇偶平面布局。
- 引擎行为细节（含 0x74 的字典/halves/table 三区重叠、0x73 从 tag+1 读控制字节、0x20 的 t2 初值与 +1 终止符等）已在 `codecs.py` 中忠实复刻，可对 0x8001E0F0 路径逐一对照。

## 三、对话文本定位

### 3.1 文本块位置

- 对话/字幕文本分散在若干场景包条目内，已知块地址（逻辑）由 `tools/decode_text.py` 的 `TEXT_SEGS` 列出（33 段，含开场第一句 0x0246915C 等）。**早期文档中的 "30 ENTRY / 62 块 / E160=0x221915C" 等地址为历史过程数据，地址基准与最终实证有出入，仅作参考**。
- 每个文本块以 `00 00` 终止符结束，终止符后为连续零填充区（`zero_span`）。
- 文本块按“条目→块”组织，同一场景包可有多个文本块；第二份拷贝的镜像条目（358-420）与其第一份（162-222）内容一致。

### 3.2 文本块内部结构（token 流）

```
[token]* [00 00]
token := 文本码(1B 或 FF xx / FE xx) | F1 | F3 | F6 | F2/F4/F5(其他控制)
```

- 每帧：`[说话人标记 kana] F3 [文本] F6` 结构（F3 前恰 1 个文本 token = 说话人标记；F6 = 帧尾）。
- `F1` = 句中停顿/翻页（按译文 ∥ 还原）。
- 每帧文本码数 ≤ 20（引擎 137 断言）。
- 全角空格 = 码 0x00。

### 3.3 与汉化补丁的关系

- `engine137.py` 的 commit 流程：读原块 → 解析 token 模板 → 用 `codetable_v3.json` 把译文编码为字节 → 镜像原控制结构重建块 → 断言新块 ≤ 原 00 终止符+零区 → 写盘 → 回读解码比对。
- 说明：**码表本身不是日文原表**，而是汉化版新码表（将日文假名位置重映射为中文新字形码），见《FONT_LOAD_DOC.md》。

## 五、如何验证（自检流程）

1. 用 `tools/extract_entries.py` 解析条目表（513 条），取任一场景包段。
2. 用 `codecs.py` 对 `[段首:段尾]` 做块流解码，直到 0x00 终止。
3. 检查输出：解出 8192 的块槽位，槽尾若为 0x22 连续 9 字节（字形空白）即疑似字形流；若含文本码（0x01-0xEF/FF xx/FE xx）即文本块。
4. 对文本块用 `tools/decode_text.py --all` 解码，输出应与 `text/dialogue_original_v3.txt` 一致（33 段）。
