# 《Crisis Beat》文本渲染引擎反汇编笔记（2026-09-13）

> 基于 SLPS_014.exe 反汇编（ePSXe/PCSX-ReARMed RAM dump + MIPS 反汇编）与多轮崩溃实测总结。
> 这些结论描述**原版日版**的文本解码/渲染实现，供研究参考；不包含任何修改镜像的 hack 成果。

## 一、文本解码器

### 1.1 跳转表与处理函数

- 文本解码跳转表位于 `0x80065678`，共 16 条（处理控制字节 F0-FF）。
- 已确认 handler：
  - `FE handler` @ `0x8009E894`：读下一字节，`字符码 = 下一字节 + 0x1E0 (480)`。
  - `FF handler` @ `0x8009E870`：读下一字节，`字符码 = 下一字节 + 0xF0 (240)`。
  - 公共写入例程 @ `0x8009E8B8`：把 16 位字符码写入显示缓冲区。
- 主文本循环 @ `0x8009EEB4`：依次调用解码器（`0x8009E7D4`）与渲染引擎（`0x8009EB54`）。

### 1.2 显示缓冲区

- 显示缓冲区基址 `0x800D22C4`（另有资料记 0x800D4C4，二者为同一区域的不同偏移记法）。
- 布局：15 行 × 15 列 × 2 字节 = 450 字节。
- 写入公式：`offset = row * 2 + col_pixel_offset * 30 + 0x800D22C4`（每行 30 字节 = 15 halfword）。
- **无边界检查**：超长文本会直接越界写，这是编码时必须保持长度约束的原因之一。

## 二、渲染引擎

### 2.1 TPAGE 支持

- 渲染引擎 `0x8009EB54` 只支持：
  - `TPAGE 5`：字符码 < 0x100（fontA 字形区）。
  - `TPAGE 29`：字符码 < 0x200（fontB 字形区）。
- **没有 TPAGE 31 路径**：码 >= 0x200（页 31 字符）在原版引擎中无法渲染（TSB31 装载器存在但不参与本路径）。
- 字符码在 UV 计算中被 `andi` 截断为 8 位：`U = (char & 0xFF) << 4`，`V = char & 0xF0`。

### 2.2 字库上传

- 字体上传例程 @ `0x8009E400`（font upload），负责把字库字形数据从 RAM 上传到 VRAM。
- 该例程存在除零 break：若字形尺寸数据为 0 会直接断（与某些零宽条目相关）。

### 2.3 字形统计

- fontA / fontB 各有约 469 / 346 个零宽条目（即码位存在但无实际像素数据），渲染时跳过。

## 三、文本段与终止符

- 文本初始化 `0x8009E704` 扫描 F3 计数段数（F3 = 段尾标记）。
- 每个文本段的正确终止符序列：`F6 FF F3`（F6 块尾 → FF 控制 → F3 段尾）。
- 若段缺少终止符，解码器在读取时会越界，曾导致启动早期崩溃（早期诊断结论，后续实验部分推翻，见下）。

## 四、崩溃排查历史与教训（记录，非 hack 成果）

以下为 2026-09-09 至 09-13 期间对「汉化版补丁崩溃」的排查记录，**仅为研究过程存档**：

1. **假设 A：EXTRA[0] 缺 F3 终止符** —— 被 v57d 实测推翻（补上终止符仍崩）。
2. **转向 TEXT[01]（0x024691E0 "なんだろ？"）** —— 开场第一句，v58/v59 均在此崩。
3. **发现 FE 编码公式错误**：曾用 `code - 0x200`，正确为 `code - 0x1E0`；已修正但实测仍崩，说明崩溃根因不止编码。
4. **最终状态**：崩溃根因**未彻底定位**，v58 的 SHA256 与全文差异仅限纯文本段（字库簇零改动），仍无法运行。

> 结论：原始日版文本系统已完全逆向（解码/渲染/装载），但「字形替换后开场崩溃」的确切根因仍未定论。任何后续研究者应以此为前提，**优先在真实模拟器上以最小改动验证**。
